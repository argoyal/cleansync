# 0.5.2: Unsubscribe, account photos, a fast offload Start, and one dead setting

Status: draft for review · 2026-10-14 · builds on [mail panel and search](2026-10-13-mail-panel-and-search-design.md), [bulk offload](2026-10-13-bulk-offload-design.md) and [model limits](2026-10-13-model-limits-design.md).

## 1. Why

The owner asked for four things:

1. **Unsubscribe.** inbox-zero had a bulk unsubscriber, and CleanSync doesn't. The owner wants to scan the whole mailbox for marketing senders they can unsubscribe from, then unsubscribe from many at once. It lives in CleanSync's part of the Mail panel, and the owner chose **inbox-zero's process** for how an unsubscribe is done.
2. **Account photos.** Settings → Accounts should show each mailbox's Google profile picture.
3. **Large offloads time out at 120 s.** CleanSync sets no 120 s limit itself. A proxy or tunnel in front of the app gives up on a request that runs too long.
   - Starting an offload does slow work before it answers: `POST /api/mail/offloads` re-runs the whole preview, which stats every `.eml` file. It then inserts one `MailOffloadItem` per mail.
   - With 50,000 mails that takes minutes.
   - The server usually finishes anyway, so an offload the owner thought failed may still run.
4. **Check that every setting is used.** One setting, **Mails per offload batch** (`mail_batch_size`), is saved but read by nothing. Offload has used a fixed 1,000 (Gmail's maximum) since 0.5.0. All other settings are used.

## 2. What success looks like

- **Finding senders.** The Unsubscribe page lists the senders that carry an unsubscribe link, with their stats, for the whole mailbox, old mail included.
- **Unsubscribing many at once.** Picking 50 senders and pressing Unsubscribe gives a result for each one: Unsubscribed, Auto-archived, Couldn't confirm or Needs you. No sender waits in a request the browser holds open.
- **Starting a big offload.** The preview and Start on a 50,000-mail offload each answer in a few seconds, whatever the disk.
- **Photos.** Each mailbox shows its Google photo in Settings → Accounts and the account switcher, or its initial when there is none.
- **Settings.** Every field in Settings changes something.

## 3. Unsubscribe: finding senders

### 3.1 Saving the header

- **Two new columns** on `mail_messages` (migration 0014), both nullable text:
  - `list_unsubscribe`: the raw `List-Unsubscribe` header, whitespace collapsed, at most 2,000 characters;
  - `list_unsubscribe_post`: the raw `List-Unsubscribe-Post` header.
  - `sender`: the lower-cased address part of `From`, so the list can group in SQL.
- **Filling them on backup.**
  - `parse_eml` reads both headers into `ParsedMail`.
  - `add_message` saves them, so new mail gets them on backup.
- **Old mail.** A one-off **header scan** fills them in for mail backed up before 0.5.2.
  - Mail that still needs scanning is marked by a new `mail_messages.headers_scanned` column (boolean, default false for old rows). New rows are written with true.
  - The scan reads each file's **headers only** (`BytesParser(...).parsebytes(raw, headersonly=True)`). It stops reading at the blank line after the headers, at most 256 KB.
  - It works in chunks of 500 rows, each committed on its own, in the background, one mailbox at a time.
  - It resumes after a restart, because unscanned rows are exactly the ones still false.
  - A file that can't be read is marked scanned with no header, so it is never retried in a loop.
  - It pauses while the mailbox's backup is running. This uses the same `mail.queue` the backup and offload use.
- **Scope.** Only mail CleanSync holds a copy of counts. That is every state that has a file: in Gmail, offloaded and deleted in Gmail.

### 3.2 The sender list

**Who is listed.**
- A sender is listed when at least one of their mails has a `list_unsubscribe` value.
- Senders are grouped by `sender`.
- Left out:
  - the mailbox's own address;
  - mail with the `SENT` or `DRAFT` label.

**Per sender, the list shows:**
- **Who:** name (taken from the newest mail) and address;
- **How much:** the number of mails, and their total size;
- **Read:** the share read, meaning not `unread`;
- **Inbox:** the share still in the Inbox, meaning `INBOX` and in Gmail;
- **Last mail:** its date;
- **Status.**

The counts take in all of CleanSync's copies of the sender's mail, in Gmail or not. The Inbox share counts only mail still in Gmail.

**Tabs** (default **Suggested**):
- **Suggested:** 3 or more mails, under 20% read, and no status. This is inbox-zero's rule.
- **All**.
- **Unsubscribed**, **Kept** and **Auto-archived**: one tab per status.

**Sort and search.**
- Sort by mails (the default), unread, newest or size.
- A search box matches the name or address.

**Paging.** 50 per page, using the existing list paging.

**Pick all.** It picks every sender in the tab and search, not just the page.

**While the header scan is running,** the page shows "Scanning old mail: N of M…" above the list. The list fills in as the scan goes.

**Speed.** The query groups over `mail_messages` with a partial index on `(account_id, sender) WHERE list_unsubscribe IS NOT NULL`. It must stay under 1 s for 200,000 mails. `test_mail_speed_big.py` gets a case for it.

### 3.3 Status per sender

- **New table** `unsubscribe_senders` (migration 0014):
  - `account_id`, `address` (lower case, unique together);
  - `status`: `unsubscribed`, `kept` or `auto_archived`;
  - `filter_id`: the Gmail filter CleanSync made, if any;
  - `method`: `one_click`, `link`, `form`, `filter` or `manual`;
  - `note`: the last result in words;
  - `updated_at`.
- **No row** means no status.
- **Kept** means "I want this mail". It is never suggested again, and it removes CleanSync's filter for that sender (§5).

## 4. Unsubscribe: what a click does

### 4.1 The job

- **Unsubscribe** works on one sender, or on picked senders (by hand or Pick all). It starts an **unsubscribe job** and returns at once.
  - New table `unsubscribe_jobs`: id, account, state, counts and timestamps.
  - New table `unsubscribe_job_items`: job, address, `outcome`, `note`.
- **The job runs in the background,** one sender after another, the way inbox-zero's bulk actions do.
  - **Progress.** A window shows it with a result per sender as it comes in.
  - **Closing.** Closing the window keeps the job running.
  - **Stop.** Stop ends it after the current sender.
  - **Restart.** After a restart, the job carries on from the senders without an outcome.
- **One job per mailbox at a time.** A second start while one runs is refused with "An unsubscribe is already running for this mailbox."
- **Activity** records each job with its counts: "Unsubscribed from 41 senders, 6 need you".

### 4.2 Which link

For each sender, CleanSync reads the `List-Unsubscribe` value of their **newest** mail that has one.
- It splits the value into `<…>` entries: http(s) links and `mailto:` addresses.
- **Body fallback.** When the header has no http(s) link, CleanSync looks in that newest mail's HTML for an unsubscribe link, as inbox-zero's `findUnsubscribeLink` does. Two kinds of link count:
  - a link whose text mentions "unsubscribe", "email preferences", "opt out" or "manage subscriptions";
  - an href containing `unsub`, `opt-out`, `optout` or `list-manage`.
  This reads the one saved `.eml`, never Gmail.
- **https before http.** An https link is tried before an http one.

### 4.3 The steps, in order

The steps follow inbox-zero, and the first one that works ends the sender:

1. **One-click request.**
   - It sends `POST <link>` with the body `List-Unsubscribe=One-Click` (`Content-Type: application/x-www-form-urlencoded`).
   - **Success:** any 2xx answer. Outcome **Unsubscribed**, method `one_click`.
2. **Visit the link.**
   - It sends `GET <link>`.
   - **Success:** a 2xx answer that is not an HTML page with a form. Outcome **Unsubscribed**, method `link`.
3. **A form on the page.** If step 2 returned HTML with a form, CleanSync handles a **simple** form only:
   - one `<form>`;
   - no password or file fields;
   - no captcha markers (`g-recaptcha`, `h-captcha`, `cf-turnstile`).
   CleanSync submits that form with its default and hidden values, and with any checkbox or radio labelled "unsubscribe" or "all" ticked. Then the **Unsubscribe** model task reads the reply page's text, trimmed to 4,000 characters, and answers `confirmed`, `not_confirmed` or `unclear`:
   - `confirmed` gives **Unsubscribed**, method `form`;
   - anything else gives **Couldn't confirm**.
   With no model set for the task, or the model paused, the outcome is **Couldn't confirm** with "No model to check the page. Open it to finish." A form that isn't simple also gives **Couldn't confirm**.
4. **No http(s) link at all**, only `mailto:`:
   - If the mailbox **allows Gmail filters** (§5), CleanSync makes the filter. Outcome **Auto-archived**, method `filter`.
   - Otherwise the outcome is **Needs you**, with the mailto address shown and the note "Write to this address to unsubscribe, or turn on Allow Gmail filters."

If every web step fails (a network error, a 4xx or 5xx answer, or a refused address), the outcome is **Couldn't confirm**, with the reason in plain words.

**Saved status.**
- **Unsubscribed** and **Auto-archived** are saved as statuses.
- **Couldn't confirm** and **Needs you** leave the status empty, so the sender stays in Suggested. The page offers:
  - **Open page**, which opens the link in a new tab, or **Write to it**, which opens the `mailto:`;
  - **Mark unsubscribed**, which saves the status with method `manual`.

**Mail is not sent.** CleanSync never sends a `mailto:` email. It has no permission to send, and inbox-zero doesn't send them either.

### 4.4 Network safety

Every unsubscribe request goes out from the owner's server. So:
- **Refused addresses.** Only `http` and `https` on ports 80 and 443 are allowed. These hosts are refused:
  - `localhost`;
  - private and loopback addresses;
  - link-local addresses;
  - CGNAT addresses (`100.64.0.0/10`, which covers Tailscale);
  - IPv6 local ranges.
- **Checking the address.** The host is resolved once, every resolved address is checked, and the connection uses the checked address.
- **Redirects:** at most 5, and each target is checked the same way.
- **Limits:** 10 s per request, and at most 256 KB read from the answer.
- **What is sent:** a plain browser-like `User-Agent`, and **no cookies**. No CleanSync or Google credentials are ever sent.
- **Logging.** A link's query string can hold the owner's token, so logs and Activity show only the host.
- **Tests.** Tests and the e2e fake web server run on `127.0.0.1`. Only the test settings can allow that, through a guard injected in code; the e2e run uses `DRIVESYNC_ALLOW_LOCAL_ACCOUNTS`, the same dev-only switch as the fake Gmail. A normal install can never turn it on.

### 4.5 The model task

- **A new model task:** `AiTaskName.UNSUBSCRIBE = "unsubscribe"`.
  - It is set in Settings → Models like **Sorting**.
  - When it isn't set, it falls back to Sorting's choice, as Writing rules does.
- **Limits.** It goes through `AiClient` with the 0.4.0 limits, so a paused model gives **Couldn't confirm** and never waits.
- **The prompt:**
  - it asks only "does this page say the email address was unsubscribed or removed?";
  - it wants a JSON answer;
  - the page text is marked as data, not instructions.

## 5. Allow Gmail filters (auto-archive)

**The permission.**
- **Scope:** `https://www.googleapis.com/auth/gmail.settings.basic`.
- **Opt-in per mailbox,** built like Allow permanent delete:
  - It is off by default.
  - It is saved in `accounts.gmail_filters` and `accounts.gmail_filters_note` (migration 0014).
  - It is on only while the switch is on **and** Google granted the scope.
- **Settings → Accounts → each mailbox** gets **Allow Gmail filters**:
  - **Off:** "Turn this on to let CleanSync keep a sender's new mail out of your Inbox when it can't unsubscribe for you." with **Turn on**.
  - **Turn on:** Google's sign-in asks for the extra scope.
  - **On:** shown with **Turn off**, which stops using it.
  - Turn off also cancels a pending Turn on, as permanent delete does since 0.5.1.
- **Losing the permission.** If Google refuses the scope (a 403 with insufficient scope), the switch goes off with a note, and Activity says so once.

**What Auto-archive does.**
- **The filter.** `users.settings.filters.create` with criteria `from: <address>` and action `removeLabelIds: ["INBOX"]`. Gmail filters only affect **new** mail.
- **Saved.** The filter id is saved on the sender's row, with status **Auto-archived**.
- **Who can trigger it:**
  - step 4 of an unsubscribe;
  - **Auto-archive** on one sender or on picked senders. That runs as the same kind of job, with outcomes Auto-archived or Needs you.
- **Filter already there.** If Gmail says an identical filter already exists, CleanSync looks it up with `filters.list` and saves its id.
- **Too many filters.** Before making a filter, CleanSync counts the mailbox's filters. At 990 or more it refuses with "Gmail allows 1,000 filters and this mailbox has N. Remove some in Gmail first." That sender's outcome is **Needs you**.

**Keep** deletes CleanSync's filter for the sender (`filters.delete` with the saved id) and saves status **Kept**.
- It needs the permission only when a filter exists.
- A filter that is already gone is treated as deleted.
- Filters the owner made in Gmail are never touched.

**Quota.** Filter calls are counted in the daily budget: create and delete 5 units, list 1.

## 6. Other actions on the Unsubscribe page

Each acts on one sender, or on picked senders:
- **Open their mail:** goes to Mail with the search `from:<address>` (one sender only).
- **Offload their mail:** opens the existing Offload dialog with the search `from:(a OR b OR …)`, or one `from:` for a single sender.
- **Delete forever their mail:** opens the existing Delete forever dialog the same way. It is only offered when the mailbox allows permanent delete, and it needs the typed count.

These reuse the 0.5.0 paths, so every safety rule stays. A pick of more than 50 senders sends one dialog per batch of 50, in turn, so the `from:` search stays short.

## 7. The Mail panel

The CleanSync group gets **Unsubscribe**, a page like **Rules**, at `/mail/unsubscribe`, placed after Rules. The order is Suggested, Rules, Unsubscribe, Offloaded, Deleted in Gmail. A count badge shows the number of Suggested senders.

## 8. Account photos

**Fetching the photo.**
- `fetch_about` asks Drive for `user(emailAddress,photoLink)`. This needs **no new scope**, because the account is already connected with the Drive scope.
- On connect, and whenever the account is checked (`last_checked_at`), CleanSync downloads the `photoLink` image. It allows up to 256 KB of image, from `*.googleusercontent.com` only.
- It saves the image as `photo.jpg` (or the type Google sent) in the account's folder under the data root, and records `accounts.photo_type` and `accounts.photo_updated_at` (migration 0014).
- No `photoLink`, or a failed download, leaves the old photo or none. It is never an error.

**Showing the photo.**
- `GET /api/accounts/{id}/photo` serves it from CleanSync itself, behind login, with a one-day cache header.
- Serving it from CleanSync keeps the page's `img-src 'self'` rule and sends no request to Google from the browser.
- The account list gives `has_photo`.
- `Avatar` shows the image when `has_photo` is set, and the initial otherwise, or when the image fails to load. It is used in Settings → Accounts and the account switcher.
- The pretend local account has no photo.

## 9. A fast offload Start

**What is slow (measured 2026-10-14).** On 41,500 matching mails in the test setup:
- finding the rows takes 0.3 s;
- writing the offload's rows takes 1 s.

What scales with the disk is the **file check**: one `stat()` per mail, in the preview and twice more in Start, because Start re-runs the preview. On Docker Desktop or a network disk each `stat()` is slow, so a 50,000-mail Start can take minutes. (This revises the first draft of this section, which moved planning into the background. The owner approved the spec before the measurement.)

**The fix:**
- **The preview and Start no longer stat each file.** A mail counts as backed up when its index row records a file (`file_path` set and `file_size > 0`). A row is only written after its file is complete on disk.
- **The real copy check is unchanged.** Each mail's file is still read, and its size and SHA-256 checked, right before it leaves Gmail (`_checked`). A mail that fails is skipped with today's reason and stays in Gmail.
- **Start writes its rows with one bulk insert** per 1,000 rows (SQLAlchemy Core `insert()`), not one ORM object per mail.
- **Delete forever in Gmail** gets the same bulk insert.
- **Start still answers in the request.** "The count changed" stays an immediate message in the dialog, as today.

**The guard.** `test_mail_speed_big.py` gets a case: a preview, then a Start, on 50,000 mails, with `file_ok` made to fail if called. It asserts no file is touched and both answer within a loose time limit.

## 10. Settings

- **Remove "Mails per offload batch"** from Settings → Mail and drop `mail_batch_size` from `app_settings.py`.
- An old saved value stays harmless in `SettingRow`.
- A `PUT /api/settings` that still sends `mail_batch_size` is ignored, not refused, so an old open tab can't break saving.
- No other setting changes. **Pause backup when free space is below** is used by the backup only, and its label already says so.

## 11. What stays the same

- **Offload and Delete forever.** Their safety rules are unchanged:
  - checked copy first;
  - the typed count;
  - Delete forever needs permanent delete;
  - Delete forever rules are never Automatic.
- **No mail sending.** CleanSync never sends mail.
- **No headless browser,** unlike inbox-zero's optional worker.
